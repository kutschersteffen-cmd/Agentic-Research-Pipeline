# Agentic Research Pipeline — Technical Reference

A comprehensive inventory of every functional module, the AI/agent stack, and every backend and frontend package this application depends on — as of the current state of `kutschersteffen-cmd/Agentic-Research-Pipeline`.

## 1. What this is

Two coupled tools for investment research at scale (designed for up to ~4,000 companies per run, currently tuned toward a ~400-company scale for the document-parsing pipeline):

1. A **Thematic Universe Builder** that turns a macro theme into a defensible, cited list of matched companies.
2. A **Data-Point Extraction Engine** that pulls schema-defined figures out of company disclosures with independent verification and programmatic citation grounding.

Around that core sit five more modules — Company Financials extraction, agentic Identity Resolution, Document Discovery, Engagement & Voting (stewardship), and Portfolio Risk & Climate Analytics — sharing one file-based storage convention and one LLM client interface.

**Storage philosophy:** everything is files — JSON/JSONL under `runs/`, `portfolios/`, `engagements/`, `ballots/`, `taxonomies/`, `data/documents/`. No database. The one deliberate exception is `DocumentContentStore`, a SQLite cache for parsed document text, added specifically to avoid re-parsing the same PDF on every run.

**Precision-first design:** every LLM call that produces a citation is checked programmatically against the source document text (never trusted on the model's say-so), every extraction has an independent verifier pass, and anything below a confidence threshold is queued for mandatory human review rather than silently included.

## 2. System architecture

```
backend/   Python — FastAPI (HTTP API) + Typer (CLI) — every agent pipeline lives here
frontend/  React + TypeScript (Vite) — authoring, monitoring, and review UI
data/documents/   local document store: manual uploads + discovery-crawler downloads
runs/             file-based run state — manifest, results, errors, review queue
engagements/      per-company engagement record store (state + append-only audit log)
ballots/          voting-instruction files, one per cast vote
portfolios/       holdings snapshots, security/company registries, climate observations
taxonomies/       versioned, ratifiable theme definitions
```

The backend and frontend are fully decoupled: the CLI and the API call the exact same pipeline functions, so nothing is UI-exclusive or CLI-exclusive. The frontend talks to the backend over a single `VITE_API_BASE`-configured HTTP boundary — no server-rendering, no shared process.

## 3. Functional modules

### 3.1 Thematic Universe Builder
Turns a macro theme ("electrification", "AI") into a defensible company list. An LLM first decomposes the theme into concrete business activities, then every company in the supplied universe is run through an **Advocate → Opposing → Adjudicator** three-agent debate (`research/match_graph.py`, a LangGraph state graph) per activity, producing a verdict, confidence, exposure estimate, and a cited rationale. Results are filterable/sortable in the UI (verdict, activity, flagged-only, confidence/exposure) and a filtered result set feeds the Extraction Engine as a new universe with one click. Runs are checkpointed and resumable (`arp theme resume`).

### 3.2 Taxonomy Library
A versioned, ratifiable alternative to a one-off theme file. Five creation methods: `industry_anchored`, `authority_source` (grounded extraction from a cited authority document), `empirical` (mined from an actual company universe), `news_transcript_mining`, and `etf_index_holdings` (derived from a fund's holdings export). Supports diffing (`compare`) and drafting a merge (`merge`) of two taxonomies, and cross-referencing every activity into NACE/NAICS/SIC/GICS standards codes — NACE/NAICS/SIC via deterministic ISIC correspondence tables, GICS via LLM classification against a fixed reference list with a required rationale (no public ISIC↔GICS crosswalk exists).

### 3.3 Data-Point Extraction Engine
Pulls specific, schema-defined data points (e.g. "green capex", forward-looking business outlook) from sustainability reports, annual reports, and earnings-call transcripts. Each field goes through an **extractor agent** and an **independent verifier agent** (`extraction/field_graph.py`), and every citation the extractor claims is checked programmatically against the real source text by `grounding.py` — never trusted on the LLM's self-report. A grounded citation resolves to an exact PDF page number or xlsx sheet name and opens a "view source" link straight to that location. Every field can be marked reviewed, overridden, or rejected, with an append-only per-field audit trail.

**Planning, checks and routing (E62–E68, no model calls).** Before extracting, the pipeline plans per company (`planning/`): *entity confirmation* marks each document `confirmed`, `ambiguous` or `mismatch` against the company's identifiers, and mismatched documents are held out (listed as `held_documents`; if every document is held, every field routes `hold` with `entity_mismatch`); *applicability* rules (sector codes, countries, regimes) skip a field that cannot apply, with route reason `not_applicable_by_rule`; a *period plan* per document fixes which fiscal periods to extract; *document routing* sends each field to its preferred document types and sections. A field whose input hash (field version, document content keys, planned periods and the effective models, thresholds, retrieval mode and XBRL setting) matches the last run's reuses that run's rows with no model call — unless those rows failed a check, a reviewer rejected one, or the run is a "Restart from here" (cache refresh). A rejected value is re-extracted, and if the answer is the same value it fails the `prior.rejected` check and routes to review, until a reviewer approves or corrects that item in a later run. After extraction, layered checks run on every value (`checks/`: 1 format, 2 numeric, 3 plausibility, 4 cross-source incl. prior period, 5 model), each `pass`, `fail` or `not_applicable` at severity `info`, `warn` or `block`; a failed `warn`/`block` check adds `check_failed`. Checks only add failures and never relax grounding. Then each row routes three ways (`extraction/routing.py`): `hold`, `review`, or `auto_accept` — the last only when the field version is released, its first audit is recorded (`POST /api/extraction/fields/{id}/versions/{v}/first-audit`), every check passes, confidence clears `auto_accept_min`, the value is grounded, and the run is not a trial (a trial sends every non-held row to review with `unreleased_version`). The route is the system's decision and lives only as `route`/`route_reasons` on the result row; `review_decisions.jsonl` stays human-only. In `company_facts` an undecided auto-accepted value shows as `auto_accepted` (no reviewer) and a held one as `held`.

*Tagged values (E29).* A field with `xbrl_tags` takes the filer's own tagged XBRL fact (`method = "tagged"`, no model call) when every planned period has one. Tagged values are reviewed or auto-accepted like any other and show in results and `company_facts`, and **publish** through a frozen companyfacts original (step 7b): `XbrlFactSource.fact_source` stores the fetched companyfacts bytes store-or-fail under their sha256 (`freeze_company_facts`), registers them as `xbrl:{cik10}:{sha[:16]}` with that `storage_uri`, and stores a rendered text, one line per annual fact (`{taxonomy}:{name} = {value} {unit} (period ending {end}, form {form}, filed {filed})`), under parser version `xbrl_companyfacts_v1`. A tagged SEC citation quotes its line at its span in that text, so the lineage gate and re-grounding check it like any stored document; E51 re-grounding skips it (nothing to re-parse). Freezing is idempotent and adds no fetch (the companyfacts cache keeps the raw bytes). Without a content store and blob store, or if storing fails (logged), the citation is the old one with no `content_key`, and the publish gate refuses the candidate with `no_grounded_citation` (reported in `blocked`, never dropped silently); rows written before step 7b read that way too.

*ESEF filings (E16).* European annual reports in ESEF (inline XBRL) are read as documents: a `.xhtml` report or a zipped report package (`.zip`, its largest `reports/*.xhtml`; zip bombs are refused with the holdings intake's decompressed-size cap) parses through `ingestion/esef.py` into the visible page text plus every printed `ix:nonFraction` fact, with `scale`, `sign` and the ixt `num-dot-decimal`/`num-comma-decimal` formats applied and the exact char span the fact is printed at. Hidden (`ix:hidden`) and dimensional (segment/scenario) facts are left out. Local files, the discovery crawler and the downloader accept `.xhtml` and `.zip`. The tagged path reads a `FactSource`: SEC's companyfacts (`CompanyFactsSource`) and each ESEF filing among the company's documents (`EsefFactSource`, a full-year fact ending in the planned fiscal year, the most precise duplicate first), ESEF first for a non-US filer (a company without a CIK; an LEI alone does not put it first). An ESEF tagged value cites its printed span in the stored original (`doc_id`, `content_key`, `parser_version`, `char_start`/`char_end`, quote = the printed number), so it passes the layer-2 checks against its own caption and **is publishable**. `esef_enabled` (off by default) adds `EsefDocumentSource`, which fetches the latest report package of each company with an LEI from `esef_index_url` (default `https://filings.xbrl.org`, `GET /api/entities/{lei}/filings`; the package download is SSRF-guarded and capped at 100 MB compressed; a package URL fetched before is read from its local copy under `cache_dir/esef` instead, as long as that copy still matches its hash, so only the index is polled again), stores the original or drops the filing, and registers it like an EDGAR filing.

**Review of extracted values (step 4).** A routed `review` row opens in the workbench (§3.18) as a decision-ready *context bundle* (`review/context.py`): the value, its source text with the cited span highlighted, failed checks in plain words, the route reasons, any conflict alternatives, the prior period, what is already published, the confidence components, the item's decisions so far, and an `etag`. Spans come from the stored parsed text of the cited document, never from a re-fetch. The `ReasonCode` values the aggregator attaches are `not_grounded`, `verifier_disagrees`, `conflict`, `low_confidence` and `check_failed`; routing (`extraction/routing.py`) also queues for `unreleased_version`, `first_audit_pending`, `below_auto_accept_min`, `high_risk_not_found`, `not_applicable_by_rule` (on trial runs) and `check:<check_id>`. (`match_ambiguous` is an identity reason.) A decision is one of four strings, each with a reason code from a fixed list:
- `approve` takes reason `confirmed` and no other decision may use it; `correct`, `reject` and `escalate` take one of `wrong_value`, `wrong_unit_or_scale`, `wrong_period`, `wrong_entity`, `not_disclosed`, `bad_source`, `needs_expert`, `other`.
- `correct` carries a `corrected_value` limited to the kind's keys (a value: `value`, `unit`, `period_end`) and, for a value, a *correction citation*. The server grounds that citation against the item's stored source text with `grounding.py` and the configured fuzzy threshold, discarding any offsets the client sent. A correction is refused unless the citation grounds in one of the item's own documents; for a numeric field the corrected number must also appear in the cited text.
- The request carries the bundle's `context_etag`. If the item changed since it was loaded, the decision is refused with 409, and the decision runs under the run lock.

*Second-reviewer rules.* A first decision sets `second_required` with the reasons that hit (`escalate` never does): `correction` (any `correct`), `high_risk` (the field is `high_risk`), `published_change` (a restatement candidate, or the decision changes the last decided value of an earlier run, or overturns this item's own final outcome), `first_audit_pending` (the field version has no recorded first audit; not applied to kinds without a field or runs without a schema snapshot) and `sample` (an `approve` chosen by `sha256(item_key)` against `second_review_sample_rate`, default 0.1, so the same item key is always or never in the sample). The second review must be a different person and agrees only with the same decision (and, for `correct`, the same value). A disagreement is resolved by an approver who took part in neither review.

*Bulk accept (E61).* `POST /api/extraction/items/bulk-accept` (analyst or higher) takes `{run_id, items: [{item_key, context_etag}]}`, at most 200 items, and approves them all or none. Under the run lock it first checks every item and answers 409 naming the first one that is not a `value` item, not `pending` (or escalated), `high_risk`, has a failing check, or whose context etag is stale; a key listed twice also refuses the call. Nothing is written then. Otherwise each item gets a first `approve` (reason `confirmed`) with its snapshot, through the same path as a single decision. Items chosen by `sha256(item_key)` against `bulk_accept_sample_rate` (default 0.2), or the item with the smallest hash when none is, also get the reason `bulk_sample`. The usual second-review rules apply on top (`published_change`, `first_audit_pending`, `sample`). An item with any reason waits for a second reviewer (`first_done`); the others are final. An item's etag folds in only its own decisions, so writing one item never stales the next. Returns `{accepted, second_review}`, where `second_review` lists every item key whose decision needs a second review.

*Snapshots.* Every decision first writes the exact bundle the reviewer saw to `runs/<id>/snapshots/<snapshot_id>.json` and stores the `snapshot_id` on its decision row; `GET /api/review/runs/{id}/snapshots/{snapshot_id}` returns those bytes unchanged.

*Check effectiveness (E41).* `checks/effectiveness.py` joins each non-trial extraction run's failed checks with the effective review decisions, per check, field and field version: `fired` (the check failed on the field), `decided` (the item has an effective decision), `hits` (decided and corrected or rejected), `overturns` (decided and approved anyway), and the two rates over `decided` (0.0 when nothing is decided). `GET /api/review/check-effectiveness` (approver only; no per-user data) and `arp extract check-effectiveness` print it. A high overturn rate marks a noisy check.

*Preset schemas and two generic checks (step 7b).* `presets/registry.py` holds `PRESETS` (preset id to a builder returning a `DataPointSchema`) and `install_preset(preset_id, registry)`, which saves the built schema into the `SchemaRegistry` (a version is only added when the content changed, so installing twice is a no-op; an unknown id raises `KeyError`). `GET /api/extraction/presets` lists `{preset_id, name, field_count}`; `POST /api/extraction/presets/{preset_id}/install` (analyst or higher, 404 for an unknown id) returns `{schema_id, version}`; `arp extract presets list|install` do the same. Two layer-3 checks use new `CheckConfig` fields: `le_of` (a list; check id `le_of`, warn) fails when the field exceeds any listed sibling, naming it, and `sum_target` (check id `sum_target`, warn) fails when the `sum_of` parts plus this field do not add to `sum_target` within `sum_tolerance` (relative to the target); `CheckConfig.sum_target_field` names a sibling whose value (same period and canonical unit) is the target instead of a constant; `plausibility.sum_identity` is skipped on a field with `sum_target` or `sum_target_field`. Both are not applicable when the field's value, a sibling or a part is missing, is for another `period_end`, or has another canonical unit.

*Green and low-carbon preset (step 7b, E22 A).* `presets/green.py` builds `sch_green_lowcarbon` from the versioned criteria table `normalise/tables/green_categories_v1.csv` (`category_id,label,kind,description,include,exclude,eu_objective`; guarded by the tables manifest; loaded by the cached `load_green_categories()`): ten `green` categories (renewable energy, energy efficiency, clean transport, green buildings, grids and storage, hydrogen, CCUS, low-carbon materials and products, circular economy, water and pollution control) and one `transition` row. Fossil gas counts only as the transition row's defined case; nuclear is in every green category's exclude rule and is recorded in the transition row, flagged by name in the quote. `eu_objective` uses the codes `ccm, cca, wtr, ce, ppc, bio` (`;`-separated). A new category means a new table version and so a new schema version. For each metric `m` in `revenue, capex, opex` the 19 fields, all `required=False` drafts, are `{m}_total`, `green_{m}_total` (`sum_of` the category fields, `part_of={m}_total`), `green_{m}_share_pct`, `transition_{m}_total` (`part_of={m}_total`, never added to green), one `green_{m}_{category_id}` per green category, `green_{m}_eu_aligned`, `green_{m}_eu_eligible_not_aligned`, `green_{m}_eu_not_covered` (the last carries `sum_of` the other two and `sum_target_field=green_{m}_total`, so the three EU statuses must add up to the green total), `green_{m}_framework` (`own_definition, eu_taxonomy, icma_gbp, climate_bonds, china_catalogue, other`) and `green_{m}_definition` (quoted). Every field's extraction instructions name the table and its version and the include and exclude rules of its category (all green categories for the green total and the three EU-status fields, the transition row for `transition_{m}_total`; the share, framework and definition fields name the table only), and ask for all green amounts whatever the framework, including those not aligned with or not covered by the EU Taxonomy. Currency fields have no canonical unit: values stay in the reporting currency with the scale applied, and are never FX-converted; the instructions ask for the ISO 4217 code with a separate scale word. With no field unit, `normalise/value.py` now stores a known factor-1 unit under its canonical code from `units_v1` ("€" and "EUR" both become `EUR`, "tonnes" becomes `t`) without changing the value; other units keep their text, and ambiguous ones (`$`) still fail. `green_summary(fields)` returns, per metric and `period_end`, `green_total`, `aligned`, `share` (reported, else green over total when the units match) and `beyond_taxonomy = green_total - aligned` (`None` if either is missing); a negative value is kept and flagged `aligned_exceeds_green`, and different or missing canonical units give `None` with flag `unit_mismatch` (a raw value counts only when it has a canonical unit). `GET /api/extraction/runs/{run_id}/green-summary` returns these rows for every company in the run (`{rows: [{company_id, name, metric, period_end, unit, green_total, aligned, share, beyond_taxonomy, flag}]}`, 404 for an unknown run).

*EU Taxonomy reported KPIs preset (step 7b, E22 B).* `presets/eu_taxonomy.py` builds `sch_eu_taxonomy`, extracted apart from the green schema: the shares and totals a company prints in its mandatory Article 8 KPI tables, never derived. For each `k` in `turnover, capex, opex` (all `required=False` drafts): `eut_{k}_aligned_pct`, `eut_{k}_eligible_not_aligned_pct`, `eut_{k}_not_eligible_pct` (`sum_of` the other two, `sum_target=100`), `eut_{k}_aligned_{obj}_pct` for `ccm, cca, wtr, ce, ppc, bio` (`part_of` the aligned share; no sum check over objectives, since multi-objective activities make it unreliable), `eut_{k}_enabling_pct` and `eut_{k}_transitional_pct` (`le_of` the aligned share) and `eut_{k}_total_amount` (currency, the denominator, ISO 4217 unit, no FX). Also `eut_nuclear_gas_reported` (`yes, no, not_disclosed`; Complementary Delegated Act Template 1) and `eut_reporting_year` (date). `green_summary(fields, eu_taxonomy_fields=None)` uses the Taxonomy run's aligned amount (aligned % x total amount, same period; turnover maps to revenue) as `aligned` only where the green run has no `green_{m}_eu_aligned`; the amount carries the total's currency unit, so a unit differing from the green total gives `beyond_taxonomy=None` with flag `unit_mismatch`. `GET /api/extraction/runs/{run_id}/green-summary` takes an optional `eu_taxonomy_run_id` (404 if unknown), matching companies by `company_id`.

*ESG in executive remuneration preset (step 7b).* `presets/remuneration.py` builds `sch_esg_remuneration` (all `required=False` drafts; routing prefers `DEF-14A`, then `10-K` and the sustainability report, with remuneration-report section hints): `rem_esg_in_pay` (`yes, no, not_disclosed`) and, for each scope `sc` in `ceo, exco` (the executive committee is extracted only where its terms are disclosed separately, never copied from the CEO) and plan `p` in `sti, lti`, `rem_{sc}_{p}_esg_present`, `rem_{sc}_{p}_esg_metrics` (`;`-separated names), `rem_{sc}_{p}_climate_related`, `rem_{sc}_{p}_climate_metric_types` (`;`-separated from `emissions_reduction, renewable_share, green_revenue_or_capex, sbti_target, transition_plan_milestone, energy_efficiency, other_climate`), `rem_{sc}_{p}_mechanism` (`weighted, multiplier, underpin, discretion, none`), `rem_{sc}_{p}_esg_weight_pct` (0-100), `rem_{sc}_{p}_climate_weight_pct` (`le_of` the ESG weight), `rem_{sc}_{p}_multiplier_min` (`le_of` the max) and `rem_{sc}_{p}_multiplier_max` (unit-less factors without an "x" unit, 0-3, so both keep an empty canonical unit and the `le_of` check runs), `rem_{sc}_{p}_multiplier_direction` (`up, down, both`) and `rem_{sc}_{p}_has_multiplier_also` (`yes, no`). Derived values are never extracted: `remuneration_summary(fields)` returns per scope (`ceo`, `executive_committee`), plan and `period_end` the `esg_in_pay` (same period, else the latest disclosed), mechanism, weight, multiplier range and `effective_weight_pct` (the weight for `weighted`; for `multiplier` the largest payout swing `max(max-1, 1-min) x 100`; `None` for underpin, discretion and none) with `threshold_class` `10_or_above` when it is 10.0 or more (exactly 10 counts as above) and `below_10` otherwise; a weighted metric with `has_multiplier_also == yes` keeps the weight and adds the note `also has an ESG multiplier`. `GET /api/extraction/runs/{run_id}/remuneration-summary` returns these rows per company (404 for an unknown run).

*Reviewer quality loop (E56).* `review/quality.py`. `arp golden-set seed-known-answers [--count N] [--seed S]` seeds known-answer items as one ordinary trial extraction run (`params.trial`, so never published): each item is a gold case (the bundled set plus the deployment's grown set) with half carrying the gold `expected_value` and half a wrong copy (a numeric value times 10 and 0 as 1, a flipped boolean, a text value as not disclosed), built through the real aggregate, checks and routing steps, its document text registered in the content store. Without `--count` it seeds `known_answer_rate` (default 0.05) times the open review items, at least one. Which items are known answers lives only in `review_quality_dir/known.jsonl` (`item_key`, `run_id`, `case_id`, `expected_value`, `perturbed`); the items, context bundles and source pages carry no marker. `GET /api/review/quality` (approver only) lists per reviewer, grouped by user id and shown by name only: `decisions` (every decision row), `agreement_rate` (first decisions that agree with the item's effective final decision, over first decisions on final items), `overturn_rate` (first decisions a later second or resolution decision in the same round disagreed with, over first decisions), `known_answer_items` and `known_answer_accuracy` (the reviewer's latest decision per known-answer item; right is approve on an unperturbed item or a correction to the expected value on a perturbed one). When a second reviewer confirms a `correct` first decision (`second_done`), the correction is appended to `review_quality_dir/extraction_cases.json` as a `GoldenSetCase` (field definition, the first decision's grounded correction span from the server-side row plus the evidence page text, corrected value; skipped when that text does not state the corrected number, and for known-answer items), which `arp golden-set run --cases` reads; the bundled set is never written. E56's "prompt examples" are deferred: the gold set grows, the extraction prompts are unchanged. Seeded rows carry the provenance a real row of their risk class would (a high-risk field's verifier prompt version is the extractor prompt's, as blind verification runs it); system rows (`user_id == "system"`) are not counted as a reviewer.

*Error analytics (E59).* `review/analytics.py`. `monthly_totals(run_store, month)` counts the reviewer decision rows whose `decided_at` falls in `YYYY-MM`, across non-trial extraction runs (known-answer runs are trial runs), per `(field_id, model, doc_type, reason)`: `model` is the result field's `provenance.extractor_model` and `doc_type` its first citation's; both are null when the item no longer joins to a result. System rows (`user_id == "system"`, such as the `span_moved` escalation a parser upgrade appends) are not reviewer decisions and are excluded. Legacy rows without a `reason_code` (written before reason codes existed) are excluded too. `GET /api/review/analytics?month=YYYY-MM` (approver only; no per-user data) and `arp extract review-analytics --month` return it. `ReviewAnalyticsScheduler` (`review_analytics_schedule_enabled`, off by default; state in `review_analytics_state_dir`) runs daily and, the first day after a month ends, writes that month to `review_analytics_dir/{month}.json` once (`last_month` in its schedule config).

**Pipeline view (Extraction screen).** Every profile (custom schema, Financials, TNFD, Transition Plan) starts from `POST /api/extraction/start`, on an uploaded list or a single company. The screen draws the profile's steps as a node diagram, read from the compiled per-item LangGraph (`extraction/steps.py::pipeline_shape`) so it cannot drift from what runs, followed by the company record and the rules step.
- *Steps before extraction* (`extraction/pre_steps.py`), each switched on per run and off by default: **Identity** (website and SEC CIK via the identity resolver; a rule match — exact LEI, identifier map, supplied identifier or a single exact EDGAR name match — is used even when it is flagged for identity review, and an adjudicated match only when resolved at or above `identity_resolution_confidence_threshold`; entity confirmation still checks every fetched document), **Content search** (homepage, then a crawl for report links), **Document management** (download what was found into the company's folder, record new and changed documents, count documents and bytes), **Parse & index** (parse and chunk every document once, so each item's evidence step reads the cached text). They run per company ahead of the per-item graph and reuse the Identity Resolution and Document Discovery code. A step fails when it raises or produces nothing the next step can use: an unclear identity, no homepage or report links, no documents, nothing parsed. The company then stops at that step, with no extraction, and an error report goes to the run's review queue (`PreStepFailed`, a `batch_runner.ReviewRequired`). The report names the step and the error, and includes what the earlier steps found. The company shows as "review", not "failed"; once the cause is fixed, restart it from that step. Each step reports what it found to the step view.
- *Before a run*, clicking a step edits its settings for that run only (`StepSettings`: hybrid search, XBRL facts, extractor and verifier models, quote-match and review thresholds). The run stores what it used in `step_settings.json`.
- *During and after a run*, each step shows items, share, and time per item, for the whole run or one company. `orchestration/step_tally.py` counts node visits as items stream through their graphs; the counts are live in memory and saved to `step_counts.json` when the run finishes.
- *Stop and restart.* Stop is the run's soft cancel: companies in flight finish, and no new ones start. "Restart from here" (`POST /api/extraction/runs/{id}/restart`) starts a new run with the same inputs, for every company or only the selected one. Steps before the chosen one replay from the document and LLM caches; the chosen step and every later one run afresh (`restart_overrides`: document cache off from Find evidence, LLM cache refresh from Extract/Answer, verifier-only refresh from Verify). A refresh skips reading the cache but still writes to it. Restarting from the rules step rescores the same run instead.

### 3.4 Company Financials Extraction
Pulls disclosed business segments (name, description, revenue, operating income, assets), total CapEx, and total R&D — each spend figure with a grounded description of what it funds and any disclosed category breakdown (e.g. maintenance vs. growth capex) — in a single combined pass per company (one document fetch, one evidence-gathering step, one extractor+verifier LLM call pair instead of three separate ones). A segment/figure not explicitly disclosed is left null, never estimated.

### 3.5 Company Identity Resolution *(agentic, added this session)*
Resolves a list of bare company names to a real, verified website/CIK before any document-discovery run. Match rules run first with **zero LLM calls** (`discovery/match_rules.py`): an entry in the identifier map (the security master, checked first: its internal issuer id wins, LEI included), an exact LEI, or a supplied website/CIK resolves the company (`match_rule` `identifier_map`, `exact_lei`, `supplied`). A single exact SEC EDGAR title match is `name_only`: it fills the CIK but is always flagged for review. Only genuine ambiguity (no match, multiple matches, or a non-exact single match) escalates to one `adjudicate_identity` LLM call (`discovery/identity_graph.py`, a LangGraph state graph), whose result (`ambiguous`) is always flagged too. The LLM's self-reported website/CIK is itself re-verified against real signals in code and force-downgraded to `UNCERTAIN` if unbacked. Nothing ambiguous is ever silently guessed — it lands in the Review Queue.

Identity items review through the workbench like any other kind (§3.18): `approve`, `correct` (a `corrected_value` of `resolved_website` and/or `resolved_cik`, with a comment naming the source, since there is no source text to cite), `reject` or `escalate`. The run-level review routes for identity are gone; `arp identity review` (§8) uses the same decision rules.

### 3.6 Document Discovery
Resolves each company's investor-relations site (from a supplied URL or a best-effort web-search fallback), does a bounded, same-domain, robots.txt-respecting crawl for annual reports / sustainability reports / proxy statements / investor presentations / transcripts, and downloads matches — runs manually or on an APScheduler-driven interval, raising a webhook event when something new appears. A reachable-but-unmatched company and an unreachable one are reported distinctly.

*ESEF feed polling (E16).* With `esef_enabled` (off by default), each discovery pass also asks the ESEF filing index for the latest filing of every company with an LEI (`poll_esef_filings` in `discovery/change_detector.py`, through `EsefDocumentSource`) and records it like a crawled document, so a new or changed filing raises a `new_document`/`updated_document` event. Any polling error is logged and the company's crawl result is kept.

*Event-driven refresh (E20).* With `event_refresh_enabled` (off by default) and a non-empty `event_refresh_schema_ids`, every new or updated document that discovery or the extraction *Document management* step records starts one extraction run per issuer and configured schema (`discovery/refresh.py`, called through the `ChangeDetector` `on_events` hook, whose errors are logged and never fail discovery). A schema that is unknown or not released is skipped with a warning. A refresh raised from inside an extraction run skips that run's own company and schema, since the run already uses the document. The company is the discovery universe's entry (`discovery_schedule_universe_path`) when it has one, else the event's id and name. Each run is created with `create_extraction_run` and launched on the job launcher. `event_refresh_state_dir/fired.jsonl` records every run fired, keyed on (company, schema, document sha256), so the same filing never starts a second run, and at most `event_refresh_max_runs_per_day` (default 20) runs start per UTC day. The CLI commands that can raise a refresh (`arp discover run`, `arp extract run`, `financials-run`, `tnfd-run`) wait for the runs they started before exiting and print their run ids.

### 3.7 Indirect Exposure Tier *(opt-in)*
Scores a company's *structural* supply-chain exposure to a theme via input–output propagation (Leontief inverse over an OECD ICIO extract), catching companies whose disclosures are silent about a theme but whose economic position says otherwise. Purely quantitative — zero LLM calls in the computation itself.

### 3.8 Revenue/CapEx Exposure Cascade *(opt-in)*
A structured revenue/CapEx data catalogue resolves exposure with zero LLM judgment where possible, falls back to grounded extraction from disclosures, and only then falls back to the qualitative Advocate/Opposing/Adjudicator debate — a hard disclosed number is never second-guessed by a categorical LLM judgment over the same question.

### 3.9 Engagement & Voting (stewardship module)
- **Engagement**: per-company issue tracking with milestone progression, an escalation ladder, correspondence, and commitments, plus controversy-trigger scanning and LLM-drafted engagement dossiers (`engagement/`). Every send/decide checkpoint is a human action.
- **Voting**: proposal extraction from proxy statements, policy-rule + LLM-judgment vote recommendations (`voting/policy_agent.py`, `proposal_agent.py`, `ballot_graph.py`), mandatory human review of every ballot item, then casting.

Both share one file-based engagement record store (current state + append-only event log) and are backend/CLI/API-complete; voting has a frontend page, engagement's UI is the dashboard page plus a shared issue panel component.

### 3.10 Portfolio Risk & Exposure Monitoring
Aggregates holdings across every portfolio via a deterministic (zero-LLM) engine, groupable by portfolio, asset class, issuer, sector, or country. Includes an Analytics Builder and a natural-language Q&A agent ("how many EUR million of exposure to BMW") where the LLM only drafts the structured query — the engine computes the actual number. An Entity Resolution layer maps free-text security/issuer references to the internal company registry, surfacing anything below a confidence threshold in a dedicated review queue.

**Holdings intake (step 5, E77).** `POST /api/holdings/upload`, `arp holdings import` and the monthly API pull all go through `holdings/intake.py:ingest`; the Holdings tab shows each holder's status.
- *Files.* CSV or XLSX, read through a JSON provider mapping (`holdings/mappings/<provider>.json`: column names, `decimal`, `weight_unit`, `sheet`; default `default`). The upload is capped at `max_upload_bytes`; an XLSX may inflate to at most 200 MB (and no member over 10 MB may exceed 100:1), a cell holds at most 10,000 characters, and a file has at most 200,000 rows. Formulas are never evaluated. Templates: `GET /api/holdings/template`, `arp holdings template`.
- *Validation* covers the whole file and returns every row error, and any error rejects the file: ISIN check digit, LEI check digits, duplicate positions, non-finite numbers, negative weights, weights summing to 100 +/- 0.5 %, `as_of` not in the future. `as_of` must be strict `YYYY-MM-DD`. **FX is never invented**: a non-EUR portfolio row needs `fx_rate_to_eur`, a EUR row must carry 1 (or none, which becomes 1), and a missing rate stays `None`.
- *Identity.* A valid LEI on the row wins, then the identifier map (ISIN to LEI on the as-of date), then an approved `security` correction, else a provisional `ARP:<uuid5>` issuer key and a `security` review item (`isin:<ISIN>`, in a `holdings` run, workbench kind `security`; one open item per ISIN). A correction feeds holdings only (`isin_decisions`), not the identifier map.
- *Precedence and override.* A holder is `file` or `api` (`PUT /api/holdings/holders/{kind}/{id}`, approver). An API pull is refused for a file holder. A file for an API holder is refused once that month has API data, unless an `override_reason` is given.
- *Revisions and audit.* Each write is a new write-once revision (`portfolios/holdings/revisions/...`); identical content returns `unchanged`. Every write appends an `audit.jsonl` row (user, role, source, file hash, override reason).
- *Groups and GICS (E23).* `POST/GET /api/portfolio/groups` and `GET /groups/{id}` save and read named sets of portfolios, companies or securities (`PortfolioGroup`, stored in `portfolios/groups.json`; analyst to save, any signed-in user to read; `created_by` is the name, never the user id). Members are stored deduplicated and sorted, and a save under an existing `group_id` is a new version where the latest wins. Aggregation also groups by `gics_sector`, `gics_industry_group`, `gics_industry` and `gics_sub_industry`: the company's 8-digit code (from the user-supplied `company_gics_path` CSV, `company_id,gics_code`) is cut to 2/4/6/8 digits and labelled from `gics_reference_path`. GICS is licensed, so no data ships; with either file unset or missing the value is `None` ("(unresolved)").
- *Q&A audit (E25).* `POST /api/portfolio/ask` and `POST /api/bi/ask` append one row per call to `portfolios/qa_audit.jsonl` (`qa_audit_path`): `{at, endpoint, user_id, user_name, question, answer_sha256, vintage, error}`, written in a `finally` so answered, unresolvable and failed asks are all recorded (an exception still reaches the caller; a failed audit write is logged, never raised). `vintage` holds `holdings_as_of` for portfolio answers and the dashboard slug and id for BI. `GET /api/portfolio/qa-audit` (approver only) returns the rows newest first without `user_id`.
- *Staleness.* `GET /api/holdings/holders` flags a holder `stale` when its latest `as_of` is before the previous month end. The index engine's own indices are not in `index_holdings` yet; only holders imported through this intake are.
- *Pull.* `POST /api/holdings/holders/{kind}/{id}/pull` and `arp holdings pull` fetch the frozen snapshot of another instance (`holdings_api_url`, `holdings_api_token`), keep only rows dated `as_of`, and use the same validation and intake. A failure flags the holder and the previous month stays readable; a malformed upstream answers 502.

### 3.11 Climate Analytics
A sub-module of Portfolio Risk: weighted-average carbon intensity (WACI), PCAF-style financed emissions, and data-coverage reporting, sourced from a mock internal ESG API and cross-validated against the Extraction Engine's independent read of the same companies' disclosures — a mismatch between the two sources is surfaced, not silently resolved.

### 3.12 Transition Plan Assessment
A direct replication of Colesanti Senni, Schimanski, Bingler, Ni & Leippold (2024): scores a company's climate disclosures against the paper's 64 fixed indicators (Target/Governance/Strategy/Tracking), each classified "talk" (future target) or "walk" (concrete, verifiable activity), one grounded RAG verdict (YES/NO/NA) per indicator. Unlike the paper's tool, every citation is independently re-verified against the source document by the same programmatic grounding check used everywhere else here, rather than trusted from the model's self-report.

### 3.13 Transition Barrier Assessment
The sector-level counterpart to 3.12: where that asks whether a company is credible about transitioning, this asks whether transition is feasible in that sector and region at all. A curated 105-cell matrix — 35 criteria across 9 hard-to-abate sectors x Technology/Regulation/Demand & Economics, each rated H/M/L for the EU, US and China — with per-cell evidence, a confidence tier, a last-verified date and 86 verified sources behind it. Note H means transition is *more* feasible (fewer barriers). Staleness is tracked separately from confidence, since a high-confidence rating can simply be old. The refresh pipeline currently covers only the 15 EUR-Lex `legal_regulatory_text` sources (stable ELI/CELEX identifiers); `GET /api/transition-barrier/refresh/coverage` reports the other 71 as manual rather than silently skipping them. A refresh may propose a rating change but never applies one — candidates go to the run's review queue. See `docs/TRANSITION_BARRIER_ASSESSMENT.md` for the full criteria and source lists.

### 3.14 Presentation & Reporting Tool
Turns qualitative findings and uploaded CSV/XLSX datasets into a pptx/docx/pdf for a stated audience. Exactly one LLM call (the Content Planner) drafts a structured `ReportPlan`; everything after it is deterministic rendering, and the plan can be reviewed or hand-edited via `GET`/`PUT /api/reports/{id}/plan` before the final render. A `.pptx` template can be ingested first so the output reuses its layouts, theme colors and fonts, extracted deterministically via python-pptx.

**House decks.** With `output_format=house_deck` the tool builds a slide deck in the app's own design system (`reporting/style/tokens.json`, Geist and Hanken Grotesk embedded, rules in `DESIGN.md`) instead of a `ReportPlan`. `LayoutInstructions.theme` is `light` or `dark`.

1. **Storyline.** `create_and_plan` makes one LLM call for a draft storyline (a headline and a purpose per slide) and stops at `STORYLINE_READY`. `arp report plan` drafts it; people edit it in the UI or with `PUT /api/reports/{id}/storyline` (there is no CLI edit command).
2. **Approve.** `POST /api/reports/{id}/storyline/approve` or `arp report approve <id>` runs the build in `house_pipeline.py`: fill each slide (`slide_fill.py`, headlines are kept as approved), lint and rewrite (`lint.py`), fit to the layout (`fit.py`), render PNGs, one vision QA call (`visual_qa.py`), then write `output.pdf` and `output.pptx` (`house_pptx.py`).
3. **Findings.** Every stage's findings are saved in `findings.json` (`GET /api/reports/{id}/findings`); files download with `GET /api/reports/{id}/download?file=`.
4. **Re-run.** `rerun` (`arp report rerun <id>`, or `ReportScheduler` via `arp report schedule`) makes a new report from an approved storyline, reloads the datasets behind its `run_refs` (`adapters.py`) and sets `rerun_of`. If a number in an approved headline is no longer in the data it stops at `STORYLINE_READY` for a person to fix.
5. **No-LLM paths.** `render_from_plan` on a house deck re-renders its saved `deck.json` (approving a `FAILED` report that has one does the same). Separately, `deck_compat.deck_from_plan` turns a hand-built `ReportPlan` into a house `Deck`, which the stewardship client report (`stewardship/client_report.py`) renders with the house renderers.

Limits: 3 fit passes, 2 lint-rewrite rounds, 1 QA round, and QA looks at no more than 20 slides. Known gaps: the pptx names the fonts but does not embed them, so a machine without Geist falls back to its default; a decision ref points at an immutable published snapshot, so a re-run on a newer decision needs a new ref; there is no adapter for portfolio or climate analytics, which are computed on request and have no stored result. `tests/test_reporting_golden_briefs.py` runs one deck of each kind (free-form, pipeline, periodic, stewardship) through real Chromium.

### 3.15 Investment Strategy Replication
Reduces an academic outperformance paper to an executable `StrategySpec` through the same extractor/independent-verifier/grounding pipeline used elsewhere, then backtests it deterministically (zero LLM calls in the computation) in-sample against the paper's own reported numbers and out-of-sample over any later window. Carries a multiple-testing-aware significance hurdle, a Deflated/Probabilistic Sharpe Ratio, PBO via purged and embargoed CSCV, and a regime-stratified breakdown. Human gates: a drafted spec must be reviewed and approved (re-checked server-side) before a backtest can run.

### 3.16 Emerging Themes Scanner
The bottom-up counterpart to the Thematic Universe Builder. Ingests EDGAR full-text search, GDELT and regulatory RSS across a universe, tags each mention into grounded evidence, clusters the tags, and tracks cluster lineage across ISO weeks (birth/continuation/merge/split) so novelty is measured against the prior period. Clusters are scored on velocity, breadth, persistence, novelty, materiality and contradiction; the promotion gate is the **action score** — the share of evidence describing something a company *did*, optionally corroborated against real SEC XBRL capex/R&D movement — so mention counts alone cannot produce a candidate. A two-tier engine classifies each company's role in a candidate theme with a risk/momentum/evidence-quality triple, leaving the full Revenue/CapEx/Demand/Enablement cascade to Tool 1 once promoted. Promote, reject and disconfirm are all human decisions and all require a recorded written reason; contradiction evidence is retained and displayed even on promoted candidates. See [`EMERGING_THEMES_VOCABULARY.md`](EMERGING_THEMES_VOCABULARY.md).

### 3.17 Standing agents (propose, never auto-apply)
The **Taxonomy Researcher** and the **Calibration Agent** (`agents/`) run on a schedule and surface proposals — candidate taxonomy activity/source updates, and confidence-calibration drift against reviewed outcomes — for a human to accept or discard. Neither writes to the taxonomy library or to settings on its own.

### 3.18 Cross-cutting: orchestration, review, monitoring
Every run type (`theme`, `extraction`, `financials`, `voting`, `identity`, `discovery`) shares one checkpointed/resumable batch-runner: results append to `runs/<run_id>/results.jsonl` per company as they complete, so an interrupted batch resumes without redoing finished work. Any running/pending run can be cooperatively cancelled, and any batch run resumed (see Durable jobs, §8). The **Review Queue** is the single human checkpoint for anything flagged, ungrounded, or low-confidence across all five review-producing run types; for extraction runs it holds the rows routed `review` (see §3.3), while `auto_accept` rows skip it and `hold` rows wait on their held documents. The **Dashboard** leads with what waits on a person (ballot items and flagged items awaiting a decision), then gives a live cross-pipeline view (escalations, SLA breaches, open engagement issues, currently executing and recently finished runs), polling every 3 seconds while open. Every review decision is recorded against the one "Reviewing as" name set in the sidebar, and each view has a URL (`#/voting/<run id>`, `#/review/<kind>/<run id>`) so refresh, Back and shared links land on the same place.

**Review workbench (step 4).** One router, `api/routers/review.py`, serves every item that waits on a person: `GET /api/review/items` (open items, optional `run_id`), `.../runs/{id}/items/{key}/context`, `.../source?doc_id=&page=`, `POST .../decision` and `GET .../runs/{id}/snapshots/{snapshot_id}`. It replaced the extraction and identity `runs/{id}/review-queue` and `runs/{id}/review` routes, which are removed; the other run types keep their own routes.
- *Kinds.* `value` (extraction rows routed `review`; any other non-held field of an extraction run's results, such as an auto-accepted value, can be opened and decided by its field item key but is never listed as open), `sector_code` (theme runs), `identity`, `quarantined_document` (a held document; `approve` releases it and needs the approver role, no `correct`), `restatement_candidate`, plus `other` for the legacy kinds (theme, financials, transition plan, TNFD), which still decide through their run's own review endpoint and where any decision is final. Extraction failure reports (`PreStepFailed`) are also `other` items but decide through the workbench endpoint with `approve`, `reject` or `escalate` (no `correct`, no second review): the decision is final at once, except `escalate`, which keeps the item pending until an approver decides. A sector-code decision has no consumer yet, and publishing a restatement is step 5.
- *States*, derived by folding the item's decision rows: `pending`, `first_done` (waiting for a second review), `second_done` (two reviewers agree), `disagreed` and `final`. `second_done` and `final` are the final states; an `escalate` leaves the item `pending` with `escalated` set, and an escalated item is decided by an approver. A later decision on a final item starts a new round; an item an approver resolved is re-decided only by an approver. A legacy `escalate` row now reads as `pending`.
- *Blind view.* While a `high_risk` item is `first_done`, anyone other than the first reviewer or an approver sees no first decision, so the second review is independent.
- *Roles.* Clients see a decision's role and date, its reason, comment, value and snapshot id, never the reviewer's name or user id; they get only `mine` for their own rows. Both stay in `review_decisions.jsonl` for audit.
- *Source view.* The highlight in a table cell is the cited span inside its text line; no table structure is parsed.
- *Unchanged.* Voting review (`voting/`, `#/voting/<run id>`, `arp voting review`) is outside the workbench and works as before, and `voting` runs are never listed in it.
- *Legacy rows.* Old decision rows keep their meaning. A legacy `edit` is read as `correct` (its `edited_value` as the corrected value) and, on extraction runs, still needs its co-sign (`review_cosigns.jsonl`, bound to that decision's `decided_at`) before it counts as `second_done`; other legacy decisions without a `step` are final at once. The UI no longer offers a co-sign button and offers no *Agree* for an `edit`, so an uncosigned legacy `edit` is resolved by an approver: a second reviewer's decision that does not repeat the same value as a grounded `correct` makes the item `disagreed`, and an approver who took part in neither review decides it. A second reviewer of a new `correct` can press *Agree* when the first decision is visible to them (not a blind high-risk item): it resubmits the first correction's value and its grounded span as the quote, which the server grounds again. `effective_decisions` returns `edited_value` for a `correct` row so existing readers keep working.

**Publishing (step 5).** Two layers: `company_facts` stays the extraction-record read model (every value, whatever its state); `published_facts`, `releases` and `fact_events` (Postgres, `arp db init-postgres`) hold what is released to other applications. Routes under `/api/publish`; publish and withdraw need the approver role.
- *What publishes.* Only values that are final (approved, or a grounded `correct`) or system `auto_accept`, never a trial run. Skips are reported per item: `trial_run`, `no_issuer_key` (legacy unrouted rows are never published), `not_final`, `held`, `not_auto_accepted`, `rejected`, `no_value`, `no_period`, `duplicate_key`, `older_than_published`, `restatement_pending`. A restatement publishes only after a workbench second review (or an approver's resolution); the legacy review routes (including the unauthenticated voting route) refuse extraction, identity and holdings runs and `isic:`/`held:`/`rst_`/`isin:` keys (400), so a no-step decision cannot reach it. A historic no-step decision on a value key still publishes.
- *The lineage gate.* A document's group is blocked as a whole when a citation is ungrounded or lacks a `content_key` (`no_grounded_citation`), the blob is gone (`original_missing`), the re-read bytes do not hash to the blob key (`hash_mismatch`), or its release was withdrawn (`release_withdrawn`). The blob is found through the registry (`resolve_document`): EDGAR citations key on the accession, the bytes on their own sha256, so an unmapped original fails closed. Blocked groups are listed in the response; the rest still publish.
- *Re-grounding.* A daily sample (`reground_sample_size`) re-checks published quotes against the stored text, the stored span (+/- 200 characters) first and the whole document only as fallback. Results (`ok`, `text_unavailable`, `not_grounded`, `offset_moved`, or a gate reason) are appended to `data/publish/reground.jsonl`; any not `ok` is logged and reported as `drift`. It changes no fact.
- *Re-grounding on parser upgrade (E51).* `orchestration/reground.py`. Unless `data/publish/parser_version.txt` already holds the current `parser_version()` (checked every scheduler tick, or `arp documents reground [--force]`), every extraction run's grounded field citations stamped with another parser version are re-checked: the stored original is re-parsed with the current parser and the quote grounded again, stored span first. EDGAR citations and frozen companyfacts citations (`xbrl_companyfacts_*`) are skipped (they do not re-parse here). Each outcome goes to `runs/<id>/regrounds.jsonl` (`item_key`, `doc_id`, `old`/`new` span and parser version, `outcome`). `offset_moved` and `not_grounded` queue a review item with `span_moved`, once per item and parser version (held fields are not queued); an item already decided is reopened by a system first-step `escalate` (reason `span_moved`), so it goes to an approver and leaves the effective decisions until re-decided. `results.jsonl` is never rewritten. A flagged item with no decision yet (an auto-accepted or pending value) gets the same system escalate, so it is neither published nor bulk-acceptable until an approver decides it. Trial runs (known-answer runs included) are skipped: they never publish and have no stored original. `original_missing` and `hash_mismatch` are settled (logged once, never retried: re-parsing cannot fix them); only `text_unavailable` is retried on the next run and keeps the version file unwritten until none is left.
- *Releases and versions.* One release per document per publish (`POST /runs/{run_id}`); a fact is keyed by issuer, field, period and basis, and a new value closes the current version (`valid_to`, `superseded_by`). The same value again is a reconfirmation (`reconfirmed_at`, no new version); an older observation is skipped. A restated version carries `restated` and `restated_by_doc_id`.
- *Withdrawal.* `POST /releases/{id}/withdraw` (reason required, 409 if already withdrawn or if a concurrent publish won) closes the release's current facts and restores each previous version as a copy with a new `fact_id` and `restored_from`, skipping versions of withdrawn releases. History is not reopened. Withdrawals are serialised per issuer.
- *As-of reads.* `GET /facts?as_of=` shows facts with `valid_from <= bound` and not closed by then. `valid_from` is the publication time, so a fact published after the as-of point is never shown. Timestamps are fixed-width UTC strings; `as_of` is `YYYY-MM-DD` (end of day UTC) or an ISO datetime; compact forms and overflow are 400. `/facts/{id}/lineage` and `/versions` give the history; `storage_uri` (a server path) is never returned, clients use `content_key`/`doc_id`.
- *Outbox.* `fact_events` types: `published`, `restated`, `withdrawn`, `restored`. Event ids follow commit order (one advisory lock per commit), so `GET /events?after_id=` (`read_events`) is the delivery cursor and never skips; `events_since` is only a time filter. A `restored` event carries the release id of the value's source release, not of the withdrawn one.
- *Old data.* `arp db init-postgres`, then `arp publish backfill`: it re-runs every non-trial extraction run as the system (idempotent), so decisions made later are picked up. `company_facts` and the file-based run records are unchanged.
- *Monthly snapshots (E77).* `build_snapshot` freezes `index_holdings`, `portfolio_holdings` and `esg_signals` as of a month end, as `{dataset}.v{major}.{csv|jsonl}` plus `manifest.json` (hashes, row counts, `cutoff`, `event_id_cutoff`, `supersedes`, `changes`). The manifest is written last, never over an existing one, so a revision is write-once; a month that has not ended cannot be built, and a per-month file lock allows one build at a time. A breaking schema change adds major N+1 while major N stays for a month (`retire_after`). A *correction* is a new revision (`r2`, ...) built when a fact visible at month end was restated, withdrawn or restored after the previous cut-off; holdings files are copied byte for byte, facts first published after month end never enter, and the manifest stores `event_id_cutoff`, the highest outbox event id the correction read, so the next correction counts events with a higher id. Ids follow commit order while timestamps are taken before commit, so a slow publish that commits during a correction is still counted by the next one; manifests without `event_id_cutoff` fall back to the time `cutoff`. The daily job corrects every frozen month, newest first, for the last 24.
- *Snapshot API.* `GET /api/v1/snapshots`, `/latest`, `/{month}/manifest`, `/{month}/{dataset}?format=csv|jsonl&revision=&major=`: only frozen revisions, files served unmodified with the manifest's hash as `ETag`. Access needs a grant on the user (`roles` in the users file): `snapshot_reader` for the API, plus `holdings_reader` for `portfolio_holdings`. The pull client (`snapshots/client.py`, `arp snapshots pull`) accepts https only (http only to localhost), fetches and checks every file's sha256 against the manifest before writing any, so a mismatch writes nothing.
- *Calendar triggers (E24).* `IntervalScheduler` subclasses whose config has `calendar_dates` (ISO dates) and/or `calendar_rule` (`month_end` or `quarter_end`) tick every 24 hours instead of every `interval_hours` and run only when `calendar_due` returns a date later than `last_calendar_fire`, which is then recorded. A listed date or the latest month or quarter end (rule) fires on the day, or on the next tick if that was missed, once; a rule never fires for a past period on a config that has not fired yet. Dates are validated as ISO. Off by default (both fields empty); old stored configs load unchanged. Emerging themes and portfolio monitoring have the fields.
- *The daily job.* `PublishingScheduler` (in-process, **off by default**: `ARP_PUBLISHING_SCHEDULE_ENABLED`) runs once a day: the re-ground sample (needs Postgres), the API holdings pull (from `holdings_pull_day`, default 2), the previous month's snapshot (on the `snapshot_day`-th weekday, default 1; with an API source not before `holdings_pull_day`) and corrections. The pull runs first in the same pass, and the snapshot is built with the holdings that exist: a failing pull never holds it; the holder keeps its previous month and stays flagged `stale`. r1 is not built until an hour after the month-end bound (a settle window for publishes stamped before midnight that commit after it); until then the snapshot job reports `skipped` and retries on the next tick. A failing job is recorded in the job's `last_results` and does not stop the others. Cloud storage adapters wait for the switch-on.

### 3.19 XBRL Facts
A function of its own, separate from Data-Point Extraction (§3.3). It downloads each company's SEC `companyfacts` JSON and latest 10-K (inline XBRL) as filed, extracts every tagged fact into a flat row, always resolves revenue and capex, and lets a user choose the tags to keep. The extraction pipeline is untouched and nothing here reads or writes the shared document, content or index stores: the XBRL store is an answer key for extraction runs and a tag catalogue, and it is files only (no database). All logic is in `xbrl_pipeline/`; `cli/xbrl.py`, `api/routers/xbrl.py` (same `authorize` dependency as the other routers) and the `XbrlFacts` page are thin layers over it. Two markets are built: the US / SEC regime and EU ESEF (below); other markets are later sub-projects.

*File layout (`data/xbrl/`, setting `xbrl_dir`).*
```
<cik10>/companyfacts-<sha16>.json   the SEC JSON exactly as served (named by the first 16 hex of its sha256)
<cik10>/meta.json                   source_sha, tags (null = all), company_id, company_ids (every id that fetched the CIK), company_name, fact_count, fetched_at
<cik10>/facts.jsonl                 one row per extracted fact
<cik10>/catalog.jsonl               one row per concept the company uses: fact count, first/last year, units, label
<cik10>/required.jsonl              revenue and capex per period-end year
<cik10>/annual-<accession>.htm      the latest 10-K primary document as filed
<cik10>/report.json                 accession, form, filing date, source URL, sha256, size, inline_xbrl
selections/<name>.json, .jsonl      named selections: tags and creation time; the cut facts
taxonomy/<taxonomy>-<year>.jsonl    tag registry snapshots
```
A `facts.jsonl` row carries company_id, cik, taxonomy, concept, unit, value, period_start, period_end, fiscal_year, fiscal_period, form, filed, accession and source_sha. Nothing is filtered when facts are extracted except by the user's tag choice.

*Fetch run.* A fetch is a `RunStore` run of type `xbrl_fetch` (`create_xbrl_run`, `execute_xbrl_run`), so progress, history and the manifest work as for the other functions. `results.jsonl` holds one status row per company: `ok`, `unchanged`, `no_cik` (no CIK on the company and no ticker match, or a resolved CIK that is not all digits) or `not_found` (SEC has no `companyfacts`); an exception (status `error`) is not a results row: it lands in `errors.jsonl`, and the page merges the two. Each row also carries the report outcome: `stored`, `unchanged` (same accession already stored), `none` (no 10-K found, e.g. 20-F and 40-F filers) or `error`. A report failure never changes the company's status: its facts are kept. Companies run one at a time (`concurrency=1`) with a 0.15 s pause (`FETCH_DELAY_SECONDS`) after each SEC request on top of EDGAR's own delay, below the SEC limit of 10 requests per second; 429, 5xx and transport errors are retried 3 times with exponential backoff, a 404 is final. A company is `unchanged` only when the new original has the same sha **and** the stored tag set equals the requested one, so changing the selection re-extracts. The store is keyed by CIK: an unchanged re-fetch under another `company_id` only appends it to `company_ids` in `meta.json` (no rewrite of facts, catalogue or required), and verify and `GET /required` match a company against that list. A tag selection must be `taxonomy:Concept` tokens (`parse_tag_ids`): an empty list or a bare name such as `Revenues` is refused (HTTP 400, CLI exit 2); omit the tags for All. A failing annual report download is logged with its traceback. `--refresh` builds the source with `ttl_hours=0` to bypass the 7-day facts cache. Resume (re-running a run id) skips companies that already have a result row and recomputes the manifest counts from the files, so nothing is counted twice. Final run statuses are `completed`, `partially_completed` (some companies errored) or `failed` (the task died before the batch finished). `POST /api/xbrl/runs/{id}/retry` re-runs the failed and unreached companies; it returns 409 while the run is executing (checked against the run lease, not the manifest's status).

*Selection modes.* **All** (default) writes every fact to `facts.jsonl`; **Selected tags** (`us-gaap:Revenues`, ...) writes only those concepts. In both modes the original JSON is stored in full, `catalog.jsonl` lists every concept, and revenue and capex are resolved, so the choice is never lossy. A named selection (`arp xbrl select`, `PUT /api/xbrl/selections/{name}`) is cut from the stored originals, never from `facts.jsonl` and never over the network, so it can be made at any time with any tags.

*Required items.* `required.py` uses the fallback lists `REVENUE_TAGS` and `CAPEX_TAGS` from `ingestion/xbrl.py` and writes one revenue and one capex row per annual period-end year: the winning concept, value, unit and period, or `status: not_found`. Nothing is guessed or estimated; a filer using a concept outside the lists shows `not_found`.

*Tag registry.* The dropdown offers every tag of the official taxonomies, not only those found in fetched reports. `TAXONOMY_SOURCES` in `registry.py` names the files: `us-gaap` 2026 (FASB, xbrl.fasb.org), `ifrs-full` 2025-03-27 (IFRS Foundation, xbrl.ifrs.org), `dei` 2026 (xbrl.sec.gov) and `esrs` 2023-12-22 (EFRAG, xbrl.efrag.org; the sustainability tags). `arp xbrl taxonomy update` (or `POST /api/xbrl/taxonomy/update`) downloads the schema and label/documentation linkbases and writes one snapshot per taxonomy and year with concept, label, data type, period type, balance, documentation and a deprecated flag; it never runs at page load. Parsing is guarded: files over 64 MiB (also while streaming a download) and files declaring XML entities are refused. Deprecated tags stay selectable and carry a flag. A tag in a fetched catalogue whose prefix is not a standard taxonomy (`STANDARD_PREFIXES`: the `TAXONOMY_SOURCES` keys plus `srt` and `invest`) is an **extension** (a company's own tag) and is added to the registry marked as such; `companyfacts` carries only standard taxonomies, so extensions normally do not appear. Each tag carries a **seen count**, the number of fetched companies whose catalogue contains it (0 for a tag nobody used). Search is server-side by name or label, with filters for taxonomy, seen-only and `extension_only`, paged; revenue and capex tags are pinned first on an empty search. The derived rows (seen counts, catalogue labels, snapshot rows) are cached in process per store root, keyed by the path, mtime and size of every catalogue and snapshot file, so a repeated search does not rescan the catalogues.

*ESEF (EU).* `--market esef` (API `market: "esef"`; default `sec`) fetches the latest annual report of each company from the filings.xbrl.org index (`esef_index_url`), keyed by LEI. `fetch_esef.py` looks the company up by LEI, picks the greatest plausible `period_end` among filings with both a `json_url` and a `package_url`, and downloads the filing's xBRL-JSON (stored as served, hashed) and its report package (`.zip`). `esef_json.py` flattens the JSON: numeric facts with no dimension beyond concept, entity, period and unit become rows (`form` `ESEF`, `accession` the index's `fxo_id`, `market` `esef`); dimensional and text facts are counted but not stored. xBRL-JSON period ends are the start of the next day, so one day is subtracted. `fiscal_period` is `FY` for annual durations and for instants. The LEI is normalised with `strip().upper()` and must be 20 letters or digits, else the company status is `no_lei` and nothing is written. A package download failure gives report `error`; the company status stays ok. `refresh` has no effect for ESEF; an unchanged hash and tag selection gives `unchanged`. Revenue and capex use the IFRS lists in `required.py` (`IFRS_REVENUE_TAGS`: `Revenue`, `RevenueFromContractsWithCustomers`; `IFRS_CAPEX_TAGS`: `PurchaseOfPropertyPlantAndEquipmentClassifiedAsInvestingActivities`). `meta.json`, facts, required and company rows carry `market` (old files default to `sec`); the entity directory is the CIK or LEI and the field name stays `cik`. One run covers one market.

*Files and facts.* `GET /api/xbrl/companies` lists one row per fetched company (CIK, name, fetch date, fact count, tag selection, report form, filing date, inline-XBRL flag). `GET /api/xbrl/companies/{cik}/facts` is the flat table (filters: text over label and tag id, taxonomy, form, period year, annual-only; server-side sort and paging). `.../pivot` is the by-year table: one row per tag and unit, one column per period-end calendar year (not the filing's `fy`, which also labels comparatives), annual facts only (10-K or 10-K/A, fiscal period `FY`, a duration of about a year or an instant); when a period was reported more than once the latest filed value wins. Values are shown as filed with their unit; there is no scaling. **Downloaded 10-Ks are third-party HTML.** `GET /api/xbrl/companies/{cik}/files/{kind}` (`kind`: `original`, `report`, `facts`, `required`, `catalog`) serves every file only as an attachment, with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, and the app never renders one. An unknown `kind` or a missing file gives 404, an unsafe CIK or name 400 (`safe_id`).

*Verify.* `arp xbrl verify <run_id> --map revenue=<field_id> --map capex=<field_id> [--tolerance 0.005]` and `POST /api/xbrl/verify` (`run_id`, `mapping`, `tolerance`) compare a generic extraction run (`ExtractionRecord` rows in `runs/<run_id>/results.jsonl`: `field_id`, `canonical_value`, `canonical_unit`, `period_end`) with the stored `required.jsonl`. The guard comes first: a run whose `step_settings.json` is missing, malformed or shows `xbrl_facts_enabled` on is refused (`CircularRunError`, HTTP 409), because such a run may have copied XBRL values and that flag also gates ESEF facts, so one check covers both. Runs started from the app, the API or `arp extract run` record their step settings (a CLI run writes the settings it used when it finishes; runs made before this was added have no file and cannot be verified). To verify a CLI run, run it with `ARP_XBRL_FACTS_ENABLED=false` (in the app, switch "SEC XBRL facts first" off); the refusal message says so. Per company, year (calendar year of `period_end`) and metric the outcome is `match`, `mismatch` (outside the relative tolerance, default 0.5%, or a unit that cannot be converted: detail `unit`), `missing_in_run` or `missing_in_xbrl`; the rows are written to `runs/<run_id>/xbrl_verify.jsonl`. Units are normalised first with `arp.normalise.units.convert` (a run value in `USD million` is converted into the XBRL unit before comparing); each row carries `run_unit` and the XBRL `unit`. Financials and tnfd runs are rejected with a clear error (`UnsupportedRunError`, HTTP 400, CLI exit 1). The page lists the mismatches and missing values; matches are only counted. The API `tolerance` is bounded to 0 to 1.

*API (`/api/xbrl`).* `POST /runs` (body takes `market`), `GET /runs/{id}`, `GET /runs/{id}/results`, `POST /runs/{id}/retry`; `GET /tags`, `POST /taxonomy/update`; `PUT /selections/{name}`, `GET /selections`, `GET /selections/{name}/facts`; `GET /companies`, `GET /companies/{cik}/files/{kind}`, `GET /companies/{cik}/facts`, `GET /companies/{cik}/pivot`; `GET /required?run_id=`; `POST /verify`.

*Known limits.* The generic `/api/runs/{id}/cancel` is ignored for `xbrl_fetch` runs. Concurrent `xbrl_fetch` runs each pace themselves, so N runs multiply the SEC request rate. Old `companyfacts` originals are never pruned. Saved selections can be created and listed, but their rows have no viewer in the page yet. The download endpoint's `Content-Disposition` is exposed to the browser through CORS (`expose_headers`).

*CLI (`arp xbrl`).* `fetch --universe F [--market sec|esef] [--tags A,B] [--refresh]` (ESEF needs an `lei` column); `taxonomy update`; `tags [--search] [--taxonomy] [--seen-only]`; `select --name N --tags A,B`; `files`; `verify <run_id> --map metric=field [--tolerance]`.

*Page (`XbrlFacts`, tab "XBRL Facts").* Six areas: **Fetch** (market switch SEC or EU (ESEF), choose companies, All or Selected tags, refresh, per-company status table with the report outcome, retry-failed), **Files** (the per-company table with downloads and a link to the filing on SEC.gov), **Facts** (flat and by-year views for one company, with a caption stating the fact count and whether a tag selection limited it), **Tags** (searchable multi-select dropdown `TagCombobox` over the registry, options loaded from `GET /tags` as the user types, chosen tags as removable chips, saved by name or used for the next fetch), **Required** (revenue and capex per company and year, winning concept shown, `not_found` stated in text) and **Verify** (match, mismatch and missing counts, mismatches listed, the circular-run message in plain text).

*Changes outside the package (all additive).* `ingestion/xbrl.py`: public constants `REVENUE_TAGS` and `CAPEX_TAGS` and `XbrlFactSource.fetch_company_facts_raw` (parsed JSON together with the served bytes). `ingestion/edgar.py`: `AnnualOriginal` and `EdgarDocumentSource.fetch_latest_annual_original` (a company's latest 10-K primary document as filed, with accession, filing date and URL; unlike `fetch` it registers nothing in the shared stores). `orchestration/job_manager.py`: `JobManager.mark_running` (a restart: status running, last error and cancel request cleared), used by the retry endpoint and by `execute_xbrl_run`. `.gitignore` gains `data/xbrl/`. `extraction/*` and `ingestion/esef.py` are unchanged.

*Known limits.* Taxonomies change yearly (tags are added, renamed, deprecated); a snapshot is per year and facts match tags by concept name. `companyfacts` has no dimensional facts (segment, region) and no text blocks; those need a per-filing inline-XBRL parse, planned for a later sub-project. Non-US filers have no `companyfacts`, and only the latest 10-K is downloaded (20-F and 40-F filers show report outcome `none`; a 10-K filed before inline XBRL was mandatory is stored but marked not inline). Revenue and capex tagging varies between filers. Other markets (UK, Japan), CSV export and scaling of values are not built. Searching tags and listing facts scan the files per request (see the `ponytail:` notes in `registry.py` and `views.py`).

*Operational notes.* `arp xbrl taxonomy update` and every fetch need outbound HTTPS to `xbrl.fasb.org`, `xbrl.ifrs.org`, `xbrl.sec.gov`, and `www.sec.gov` / `data.sec.gov`; ESEF adds `xbrl.efrag.org` and the `esef_index_url` host (`filings.xbrl.org`). The SEC rejects requests without a descriptive User-Agent, so set `edgar_user_agent` (`ARP_EDGAR_USER_AGENT`) to your name and contact address. Files go to `xbrl_dir` (`ARP_XBRL_DIR`, default `data/xbrl` in the repo; listed, commented out, in `backend/.env.example`). Run `arp xbrl taxonomy update` once before using the tag dropdown; until then it shows only tags seen in fetched companies.

## 4. The agent / AI stack

| Layer | Library | Role |
|---|---|---|
| LLM client | **LangChain** (`langchain-anthropic`) | Every agent call in the codebase goes through one interface, `LLMClient.complete_structured()` (`llm/base.py`) — schema-forced structured output via tool calling, a bounded self-correction retry loop on validation failure, and a disk-backed response cache. Fully provider-agnostic from every pipeline's point of view. |
| Multi-step agent control flow | **LangGraph** | Models each pipeline's per-company (or per-field/per-activity) multi-step flow as an explicit state graph with conditional/short-circuit edges: the Advocate/Opposing/Adjudicator debate, the extractor/verifier pairs (general + financials), the identity-resolution graph, and proposal extraction + policy application for voting. Company-level batch fan-out and resumability stay outside the graphs, in the file-based `run_batch`/`RunStore` layer. |
| Document chunking & retrieval | **LlamaIndex** | `SentenceSplitter` backs chunking (`ingestion/parsing.py`); a BM25 retriever backs evidence selection (`retrieval/select_evidence.py`) — deterministic and embedding-free by default, consistent with a zero-LLM-cost-in-retrieval design. |
| Hybrid semantic retrieval | **fastembed** *(opt-in)* | A 384-dim ONNX embedding model (`BAAI/bge-small-en-v1.5`, ~50MB) layered on top of BM25 when enabled — chosen specifically over the torch-based `llama-index-embeddings-huggingface` (~2GB) to keep the default retrieval path free, offline, and deterministic. |
| PDF parsing | **Docling** *(replaced pymupdf4llm this session)* | Layout-model + TableFormer-based PDF-to-markdown conversion, giving materially better table/reading-order extraction than a plain text-layer read — at the cost of a genuine ML pipeline running per page (needs a one-time model download from Hugging Face Hub on first use). Amortized across runs by the content-addressed `DocumentContentStore` cache, so it's a one-time cost per unique file, not per run. |
| Citation grounding | **None (pure Python)** | `grounding.py` is deliberately independent of all of the above: it re-verifies every citation against the original fetched document text and resolves its real location, never trusting an LLM's self-reported source. |

With `ARP_EMBEDDINGS_BACKEND=postgres` and `ARP_POSTGRES_DSN`, `content_store_for(settings)` keeps the document registry (`document_registry` table, incl. identity columns) and the chunk embeddings in Postgres; parsed text stays in SQLite as a derived cache. Existing registries are copied once with `arp documents migrate-registry` (copies rows not yet in Postgres, never overwrites; idempotent; refuses unless that backend is selected). Upgrade step: a deployment that already has SQLite registry rows must run it right after switching the backend on; until then the Postgres registry is empty or partial, and building the content store logs an ERROR (once per process) naming the command.

### Captured originals, intake and schema release

Settings (env prefix `ARP_`, see `backend/arp/config.py`):

| Setting | Default | What it holds |
|---|---|---|
| `blob_store_dir` | `data/blobs` (`/app/data/blobs` in Docker, volume `arp_blobs`) | Each collected document's original bytes, at `<dir>/<sha256[:2]>/<sha256>`. Used unless the object store is enabled (`ARP_OBJECT_STORE_LIVE_UPLOAD_ENABLED` plus an endpoint), in which case the bytes go to the bucket instead. |
| `schema_registry_dir` | `schemas/` | Versioned data-point schemas (`SchemaRegistry`); each extraction run also keeps the exact registered copy as `runs/<run_id>/schema.json`. |
| `documents_dir` | `data/documents/` | Working copies by `<company_id>/<doc_type>/`, plus two append-only logs at its root. |

- **Store or skip.** A document is collected only once its bytes are stored and read back with a matching sha256 (`upload_or_fail`). A store failure (disk, bucket, hash mismatch) means the document is *not collected* in that fetch and is retried next time; it never enters a run without a verified copy. A file already stored and still present in the store is not re-uploaded or re-read on later fetches. EDGAR filings are re-fetched and re-archived when the registry names a copy that is no longer in the store.
- **`documents_dir/_captures.jsonl`** — one row per download attempt by the discovery crawler (`CaptureRecord`: URL chain, status, response headers minus cookies, `content_key`, `storage_uri`, rights tag, `fetched_at`, `collected`, `error`). The latest row for a content key supplies the document's `published_at` when its identity is first assigned.
- **`documents_dir/_intake.jsonl`** — one row per local file intake did *not* accept: `quarantined` (empty, corrupt archive, unreadable PDF, intake error), `ocr_needed` (scanned PDF with no text layer) or `duplicate` (same bytes as another file, `duplicate_of`). These files stay on disk and are skipped by extraction. Accepted files are not logged.

Schema routes (`/api/extraction`):

| Route | Role | Notes |
|---|---|---|
| `POST /schemas/draft` | signed in | LLM draft from plain language; nothing is saved. |
| `POST /schemas` | `analyst` | Saves a new version in the registry (fields start `draft`). |
| `GET /schemas`, `GET /schemas/{schema_id}?version=` | signed in | Index, and one schema (latest version unless `version`). |
| `POST /schemas/{schema_id}/versions/{version}/release` | `approver` | Sets the version's release flag, releases its draft fields, and records `released_by` (the approver's user id) and `released_at`. |

**Trial runs.** An extraction run on a schema that is not released (any field still draft, or no release flag) is refused unless it is started as a trial. The Extraction screen sends `trial: true` automatically for an unreleased custom schema and says so before the start; on the CLI pass `arp extraction run --trial`. The flag is stored in the run manifest (`params.trial`); trial results are visible in the run views (a *trial* badge on the run in run lists and on its results) but are not projected to the Postgres company facts, so a trial never replaces a company's current fact. Restarting a custom run saved before this gate existed (its `start_request.json` has no `trial`) runs it as a trial.

**Fiscal year end.** A universe file may carry a `fiscal_year_end` column (`MM-DD`, e.g. `03-31`). Period labels such as `FY2024`, `FY24`, `Fiscal 2024`, `2023/24` or `FY2023-24` resolve to that company's fiscal year (the year it ends in); without the column a calendar year is assumed and the value carries the `fiscal_year_end_assumed` qualifier.

Every write to a shared file-backed record that could race a concurrent batch thread (run manifests, engagement records) goes through `storage/locks.py`'s `KeyedLock` — a per-key reentrant lock, so unrelated runs/companies never block each other but the same key's read-modify-write cycle can't interleave.

### Retention

`ARP_RETENTION_RUNS_DAYS`, `ARP_RETENTION_DECISION_LOGS_DAYS` and `ARP_RETENTION_ORIGINALS_DAYS` default to 3,650 days and cannot be set below 365. Age is a file's own mtime (`lstat`; symlinks are never followed). `arp retention cleanup` is a dry run unless `--apply` is given; deletion re-checks the age and refuses to delete inside the period.

- Decision logs (`review_decisions.jsonl`, `review_cosigns.jsonl`, anything under `snapshots/`) are each kept on their own period.
- All other run files go together, only once the run's newest such file (ignoring `.lock` and `.worker`) is past the runs period. Sidecar lock files are deleted with the run.
- Runs whose manifest status is `running` or `pending` are never touched.
- Stored originals in `blob_store_dir` are deleted once past the originals period; emptied directories are removed.
- Held, never deleted: any run id that is the `source_run_id` of a `published_facts` row, and any content key cited by one (needs `ARP_POSTGRES_DSN`; without it nothing is held).

### Load and cost report (E15)

`arp scale load --issuers 200 --concurrency 4,8,16 [--latency S] [--out F]` runs one `load_test` run per concurrency level against a simulated worker (no network, no API key, no LLM calls) and writes a markdown table: duration, tokens, cost, USD per 1,000 issuers, minutes per 1,000 and issuers per minute, all read from each run's manifest (`arp/scale/report.py`). The simulated figures measure orchestration overhead only; the token and cost columns are synthetic. `--live --universe P --schema P` runs real extraction instead (a trial run per level, real API spend). `arp scale report RUN_ID... [--out F]` renders the same table for existing runs. The committed local report is `docs/scale/2026-10-04-local-200-issuers.md`; `max_concurrent_llm_calls` stays at its default of 8.

### Durable jobs

`arp extract run --run-id R` (or `POST /api/runs/{run_id}/resume`, analyst or higher) continues a killed, failed, partly failed or cancelled run of any batch type: `theme`, `extraction`, `financials`, `tnfd`, `transition_plan`, `identity`, `discovery`.

- Inputs come from what the run stored at creation: `runs/<id>/companies.json` (an older theme run without one falls back to its `universe_path`), the manifest params, and the manifest's models.
- Items already in `results.jsonl`, and items stopped for review, are not run again. Plain failures are retried; their old `errors.jsonl` rows stay as history.
- The counters are rebuilt from the files: completed = result rows, failed = 0. The review count, tokens and cost are kept.
- One worker per run: every batch run, however it was started (API, CLI, scheduler, launcher or resume), holds a lock on `runs/<id>/.worker` while its batch runs (`hold_run`, taken in `run_company_batch` and `execute_discovery_run`; re-entrant within one task). A second worker on the same run raises `RunBusy`; a resume is refused (`409` from the API, exit 1 from the CLI). The OS frees the lock if the worker dies.
- Not resumable (start a new run instead): completed runs, runs created before inputs were stored, whole-pass jobs (`calibration`, `taxonomy_research`, `emerging_themes`, the barrier refresh) and `voting`.
- Nothing resumes on its own at API startup.

Full flag-level detail is in the project [`README.md`](../README.md); design rationale for every precision control is in [`METHODOLOGY.md`](METHODOLOGY.md).
