# Batch Write Retry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A short database outage (failover, dropped connection, exhausted pool) during a batch run no longer fails the run. Every database write on the batch path is retried, not only the result write.

**Architecture:** A `retrying(fn, *args, **kwargs)` helper next to `transaction()` in `arp/db/session.py` replaces the inline retry loop in `batch_runner._commit`. The batch path calls it for its writes: the result, progress, error rows, review stops and the final `finish_run`. API writes (decisions, cosigns, manual edits) stay unretried.

**Tech Stack:** Python 3, SQLAlchemy 2, pytest with the `run_store` fixture.

**Spec:** candidate 4 in `docs/architecture-reviews/architecture-review-20261011-0405.html`, narrowed by grilling:
- Q1 (b): one helper, used on the batch path only. A generic retry at the transaction is rejected: a `with` block can't re-run its body, and lost commit confirmations would duplicate decisions.
- Q2: accept a rare double count when a commit succeeded but its confirmation was lost. It is marked with a `ponytail:` comment.

## Global Constraints

- `retrying` retries exactly the exceptions `_commit` retries today: `sqlalchemy.exc.OperationalError`, `sqlalchemy.exc.TimeoutError` (pool timeout) and `sqlalchemy.exc.DisconnectionError`.
- It keeps today's values: `_WRITE_RETRIES = 3` (4 attempts in all) and `_RETRY_BACKOFF_S = 0.5` doubling per attempt. It logs a warning per retry and re-raises the last error. These constants move from `batch_runner` to `db/session.py`.
- `batch_runner` no longer imports anything from `sqlalchemy`.
- `retrying` must never wrap a call made while the same thread holds `RunStore.lock()`, because a retry can't revive a dead outer transaction. None of the batch-path calls below do.
- Unchanged: `run_batch`'s and `run_company_batch`'s signatures, and every API write.

## Review Focus

1. A write that keeps failing still fails the run after 4 attempts: the error propagates, and `hold_run` marks the run failed with it. Test below.
2. Errors that aren't connection errors (`IntegrityError`, `ValueError`, …) are never retried. Test below.
3. `sinks.append_error` and `_on_error` run on the event loop, so their backoff sleeps block it (at most 0.5+1+2 = 3.5 s during an outage). This is accepted: every other database call blocks the loop then too.
4. `test_company_batch_retries_pool_timeouts_and_disconnects` (I5) keeps passing, with its monkeypatch moved to `arp.db.session._RETRY_BACKOFF_S`.

### Task 1: One retry helper for the batch path

**Files:**
- Modify: `backend/arp/db/session.py` (add `retrying` and the two constants)
- Modify: `backend/arp/orchestration/batch_runner.py`: imports, `run_sinks` (`append_error` and `append_result` through `retrying`), `_commit`, `_on_error` (`queue_for_review` and `record_progress` through `retrying`), and the final `job_manager.finish_run`
- Test: `backend/tests/db/test_runs.py`

**Interfaces:**
- `retrying(fn: Callable[..., T], *args, **kwargs) -> T` in `arp/db/session.py`. It calls `fn(*args, **kwargs)`. On one of the three exceptions it logs a warning, sleeps `_RETRY_BACKOFF_S * 2**attempt` and tries again, for at most `_WRITE_RETRIES` retries, then re-raises. Any other exception propagates at once. Its docstring says it is only for writes that are safe to repeat. Add `# ponytail: a commit whose confirmation was lost is written twice (progress counted twice, an error row stored twice); idempotency keys are the upgrade path`.
