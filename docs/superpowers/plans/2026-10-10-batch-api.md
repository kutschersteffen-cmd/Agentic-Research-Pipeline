# Batch API for Background Runs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a pipeline run send its LLM calls through Anthropic's Message Batches API (50% cheaper), chosen per run, with no change to what the pipeline produces.

**Architecture:**
- `LangChainAnthropicClient` gets a `_send(params)` seam, and a `BatchingLLMClient` subclass overrides only that seam. It queues calls, flushes them as one Message Batch after 2 seconds with no new call (or at 10,000 requests), polls until the batch ends, and resolves each waiting call by `custom_id`.
- Batch mode is a per-run `Settings` copy (`llm_batch=True`, higher concurrency) that the factory turns into the batching client. So the pipelines themselves are untouched.

**Tech Stack:** Python 3.13, `anthropic>=1.13` (`AsyncAnthropic.messages.batches`), FastAPI, Typer, React + TypeScript.

**Spec:** `docs/superpowers/specs/2026-10-10-batch-api-design.md`

## Global Constraints

- **Flush:** after 2 seconds with no new call, or at 10,000 queued requests (API cap: 100,000 per batch).
- **Polling:** `messages.batches.retrieve` every 30 seconds until `processing_status == "ended"`. Results are matched by `custom_id`, never by position.
- **`custom_id`:** the first 64 hex characters of the sha256 of the canonical JSON of the request params (`json.dumps(params, sort_keys=True, separators=(",", ":"))`).
- **Batch log:** one append-only JSONL file, `settings.cache_dir / "llm_batches.jsonl"`. Each row is `{"batch_id": str, "custom_ids": [str], "submitted_at": iso}`.
- **Cost:** with `LLMUsage.batch` true, every token category costs 0.5×. This stacks with the cache multipliers in `arp/orchestration/cost_tracker.py`.
- **New settings:**
  - `llm_batch: bool = False` (per run, never set globally)
  - `batch_concurrency: int = 1000`
  - `batch_scheduled_run_types: list[str] = ["emerging_themes"]`
- **Run param:** `RunManifest.params["batch"] = True` marks a batch run, so that `resume_run` keeps it in batch mode.
- **UI copy:**
  - Switch label: "Batch (50% cheaper, slower)"
  - Wait line: "Waiting on batch · {n} requests · submitted {HH:MM} · Anthropic usually finishes within an hour"
  - Run History label: "batch"
- Real-time runs must behave byte-for-byte as today: same request params, same cache keys.

## Review Focus

1. **A company whose call arrives after a flush** (a straggler) goes into the next batch; it does not hang. → Task 2, `test_late_call_goes_in_next_batch`.
2. **Two identical requests in one flush** (same `custom_id`): the API rejects duplicate ids, so they are sent once and both callers get the result. → Task 2, `test_identical_requests_share_one_batch_entry`.
3. **A validation retry in batch mode:** the retry turn appends the previous assistant `response.content`, which holds SDK objects. Params must be plain JSON before hashing and submitting. → Task 1, `test_send_params_are_plain_json_on_retry`.
4. **A disk-cache hit in batch mode** must return without queueing anything. → Task 2, `test_disk_cache_hit_never_enqueues`.
5. **A restart while a submitted batch is still `in_progress`:** the client waits on it and does not resubmit. → Task 3, `test_restart_waits_on_in_progress_batch`.

### Task 3: Restart reuse, cancel, and the run's wait status

**Files:**
- Modify: `backend/arp/llm/batching_client.py`
- Modify: `backend/arp/orchestration/step_tally.py` (add hooks)
- Test: `backend/tests/test_batching_client.py`

**Interfaces:**
- Consumes: `BatchingLLMClient` (Task 2), and `RunManifest.batch_wait` plus `JobManager._update` (Task 1 / existing).
- Produces, in `step_tally.py`:
  - `record_batch_wait(wait: dict | None) -> None`: sets `manifest.batch_wait` for the current `tally_run` context; a no-op outside one.
  - `cancel_requested() -> bool`: reads the current run's `manifest.cancel_requested`; False outside a run.
- Client behaviour:
  - On submit, append the log row (Global Constraints), then call `record_batch_wait({"batch_id", "request_count", "submitted_at", "status": "in_progress"})`. Call `record_batch_wait(None)` once no batch is open.
  - On the first `_send` of a `custom_id` found in the log, attach to that batch instead of queueing it: if the batch has ended, read its result; otherwise poll it.
  - Each poll checks `cancel_requested()`. When it is true, call `batches.cancel(id)` and fail the waiting futures with `BatchRequestFailed("canceled")`.

  - `test_batch_wait_written_and_cleared`: inside `tally_run`, the manifest's `batch_wait["request_count"]` is 3 while the batch is waiting, and `None` after it resolves.
